# [Android/Clean Architecture] Data 계층 구현, 통신 최적화 및 코틀린 딥다이브

## 1. 코틀린 제네릭과 공변성 (`out T`)의 이해
`DataResult`와 같은 상태 래퍼(Wrapper) 클래스를 만들 때 `<out T>`를 사용하는 이유

* **① "데이터를 뱉어내기만(Out) 할 거야"**
  * `<out T>`는 코틀린 컴파일러에게 '이 클래스는 T라는 타입의 데이터를 밖으로 꺼내주기만(Read/Return) 할 거고 안으로 집어넣거나 수정(Write)하지는 않을 거야!'라고 약속하는 것
  * `DataResult`는 데이터를 UI로 전달해 주는 포장지 역할만 하므로 아주 적절함
* **② 에러 타입으로 `Nothing`을 사용하는 이유와 동작 원리**
  * **데이터 부재 증명:** 통신 에러가 발생한 상황에서는 화면에 전달할 정상적인 데이터(예: Book 객체) 자체가 존재하지 않음. 코틀린에서 `Nothing`은 어떠한 값도 존재하지 않음을 의미하므로 실패 상태의 제네릭 타입으로 가장 적합함.
  * **최하위 서브클래스 (Bottom Type):** 코틀린의 타입 계층도에서 `Nothing`은 `Book`, `String`, `Int` 등 존재하는 모든 타입의 하위 타입으로 취급됨
  * **공변성(`out`)과의 시너지:** `Nothing`이 모든 타입의 하위 타입이라는 특성 덕분에 공변성을 적용한 `DataResult<out T>` 구조에서는 에러를 담은 `DataResult<Nothing>` 객체를 상위 타입인 `DataResult<Book>`으로 타입 충돌 없이 안전하게 대체하여 전달할 수 있음. 결과적으로 하나의 함수에서 성공과 실패 상태를 유연하게 모두 처리할 수 있게 됨

  * **공변성이란?** 안전하게 데이터를 읽기만 한다는 보장(out)을 제공함으로써 컴파일러가 제네릭 타입 간에도 부모-자식(상하위) 관계를 매끄럽게 연결하도록 허락하는 객체지향적 장치
  
## 2. 네트워크 통신 (Retrofit & Coroutine)
* **`@GET`과 `@Query`의 역할**
  * 현업의 API 주소는 대부분 `기본주소/상세경로?옵션1=값&옵션2=값` 형태를 띰
  * `@GET("books/v1/volumes")`: 기본 URL 뒤에 붙는 **'상세 경로'**를 의미함
  * `@Query("q")`: 물음표(`?`) 뒤에 붙는 **'옵션(파라미터)'**을 의미 / `searchBooks("android")`라고 호출하면 Retrofit이 알아서 `.../volumes?q=android`라는 완벽한 주소를 조립해서 서버에 전송
* **통신 함수에 `suspend`를 붙이는 이유 (Coroutine)**(중요)
  * **문제:** 서버 통신은 와이파이 상태에 따라 0.1초 만에 끝날 수도 3초가 걸릴 수도 있음. 만약 이 통신을 안드로이드의 메인 스레드(화면 그리는 담당)에서 돌리면 통신이 끝날 때까지 앱 화면이 멈춰버림 (ANR 에러 발생)
  * **해결:** `suspend`를 붙여주면 코틀린 코루틴(Coroutine)이 "이 작업은 오래 걸리니까 배경(Background)에서 조용히 처리하고 올게!" 하고 알아서 안전하게 비동기 처리를 해줌

## 3. DTO 설계와 방어적 프로그래밍 (Nullability)
* **모든 변수 타입 뒤에 물음표(`?`)가 붙어있는 이유**
  * 서버 통신 시 가장 많이 발생하는 앱 크래시 원인이 바로 `NullPointerException` 구글 API 문서에는 있다고 적혀있어도 막상 어떤 책은 부제목(`subtitle`)이나 썸네일 이미지가 없을 수 있음
  * 이럴 때 앱이 죽지 않도록 `?`를 붙여서 안전하게 방어막을 쳐두는 것
* **`@SerializedName`을 쓰는 이유**
  * JSON 서버에서 보내주는 키(Key) 이름과 코틀린 변수 이름을 연결해 주는 역할
  * 현업에서는 서버 개발자가 `image_links`처럼 스네이크 케이스로 보내주는 걸 안드로이드에서는 `imageLinks`처럼 카멜 케이스로 받아야 할 때 이 어노테이션이 필수적으로 사용됨 (이름이 같아도 미리 적어두는 것이 방어적이고 좋은 습관!!)

## 4. 모듈/패키지 간 의존성과 Mapper
* **순환 참조 방지:** 공통 유틸리티(`DataResult`)를 `core` (또는 `shared`) 패키지에 두면, `core`가 프로젝트의 가장 밑바닥 지하실 역할을 하므로 다른 계층들이 가져다 쓰기만 하여 꼬리를 무는 순환 참조가 일어나지 않음. (과거에 썼던 `domain` 패키지에 두는 방식도 데이터가 도메인을 짝사랑하므로 훌륭한 정답임)
* **계층 간 분리 (`Mapper`):** 서버에서 받아온 지저분한 `DTO` 데이터를 `null` 처리, `https` 변환 등 정제 과정을 거쳐 우리 앱의 순수한 `Domain` 모델(`Book`)로 변환해 줌으로써 외부 환경으로부터 내부 로직을 보호함.
